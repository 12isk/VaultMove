# VaultMove safety invariants

VaultMove can delete originals ("free up space"), after which the backup drive holds the **only** copy. Every rule
below is enforced in `vaultmove/core` (no UI involvement) and has at least one automated test. Tests run on every CI
build; crash tests kill a real child process with `os._exit` at named crash points (`vaultmove/core/crashpoints.py`).

## Known limits (honest list)

* **Read-back verification goes through the OS cache.** The just-written `.vmtmp` is re-read with normal buffered
  I/O after `fsync`. To make sure deletion never relies on a cached read, offload only considers copies made in an
  *earlier* run (a later run re-hashes the vault copy again).
* **Clock jumps forward** (e.g. CMOS reset to a future date) can make files look older than they are, so they may be
  freed earlier than intended. They are still only freed after every check above passes, so the verified copy exists.
  A clock going *backwards* is safe (future mtimes are never offloaded; version folders never collide).
* **Recycle Bin mode** has a very short window between closing the guarded handle and the shell moving the file;
  size and mtime are re-checked right before. On drives without a Recycle Bin Windows may delete permanently; the
  verified copy is on the backup drive either way. Paths longer than 259 characters are not offloaded in this mode.
* Open-file backup (VSS) needs an administrator prompt and is only attempted for **Back Up Now**, never silently.
